## 2. 技术栈全景

### 2.1 分层与选型

| 层 | 技术 | 版本/要点 | 为什么选它（面试可直接答） |
|---|---|---|---|
| Web 框架 | **FastAPI** | 0.11x，ASGI | 原生 async，天然适配 SSE 流式；Pydantic 集成后校验即文档；自动 OpenAPI |
| ASGI 服务器 | **Uvicorn** | 标准 worker | 单进程够用，systemd 托管简单 |

### 亮点 1｜鉴权不是"验个签名"，而是完整可撤销体系

**（简单介绍项目）** 我最近做的项目叫百灵医生，是一个在线问诊加医药电商的移动端应用，用户是普通患者和医生，后端 FastAPI 单体 76 个接口、20 张表，前端 Vue3 加 Vant 一共 32 个页面 4014 行，后端 3632 行代码是我一个人写的，我负责后端全部接口和前端页面，从墨刀原型一路做到 CentOS7 上线。

**（应用场景，引出我们要介绍的亮点）** 上线前自测的时候出了个事：我把演示账号点了登出，拿之前抓下来的旧 token 再请求 /api/me，居然还能返回我的信息；改完密码，旧手机上的登录态也照样能用。在医疗场景里这就不只是体验问题——账号被盗之后，别人能看到你的问诊记录和处方，这是事故。所以我当时就想，鉴权这块不能只做到"验个签名"，得让 token 能被作废。

**（技术选型）** 开发前我对比了三种方案。方案一是传统 Session 加服务端存储，好处是天然可撤销，坏处是每次请求都要查会话、还得额外起一个 Redis 或者存内存，我的目标是"拷走就能跑"，多一个外部依赖就多一道部署门槛；方案二是直接调 PyJWT 这类现成库签发 JWT，好处是省事、标准化，坏处是它只负责签发和验签，撤销要另外挂黑名单，等于核心逻辑还是得自己补；方案三是手写 HS256 加版本号，坏处是要自己写六十行左右的编解码，好处是撤销语义、密钥强度校验、载荷结构全都捏在自己手里，而且零第三方依赖。

**（最终选择 + 为什么）** 最后我选了方案三。原因很直接：这个项目真正要解决的不是"能不能签发 token"，而是"能不能让 token 失效"，那撤销逻辑本来就是自己写，不如把签发一起写了，还能顺手把弱密钥挡在启动阶段。代价我也认——手写就要自己保证 HMAC 比较用常量时间、算法写死在代码里不接受外部指定。

**（实现步骤）** 第一，签发和验签用 hmac、hashlib、base64 三个标准库拼 HS256，密钥从环境变量到 .env 逐级读取，长度不足 32 位直接抛 RuntimeError 拒绝启动，不给"先上线再说"留口子；第二，users 表加一列 token_ver 版本号，签发时写进载荷，验签时比对，登出和改密就自增版本号，全端旧 token 立刻失效，历史没有 ver 字段的老 token 按 0 兼容；第三，补一个 /api/logout 显式撤销端点；密码侧用 PBKDF2-HMAC-SHA256、二十万次迭代、每用户随机盐。

**（深度优化/问题解决）**

场景一：用户改完密码，旧设备上的 token 还是有效的。
解决方案：就是上面说的 token_ver，版本号一加，旧 token 验签时比对不上直接 401，不用去维护黑名单，也不用等它自然过期。

场景二：库里存的是老格式密码（sha256 加固定前缀），直接换算法会导致所有老账号登不上。
解决方案：做成惰性迁移——登录时先用老格式校验，校验通过后立刻用 PBKDF2 重算并覆盖写回，用户无感，我也不用停机跑迁移脚本。

**（对了，我再补充一点）** 面试官常问为什么不用现成 JWT 库，我的回答是：六十行就能覆盖我需要的能力，而这套撤销语义如果基于库来做反而要绕它的扩展点；另外每请求会多一次主键查询去比对版本号，这个代价我清楚，生产上我会把版本号放 Redis 缓存，读一次就够。

**（最终结果）** 三条硬指标都能现场复现：伪造或篡改签名返回 401；登出之后拿旧 token 访问 /api/me 返回 401；跨用户读别人的订单返回 404。这三条我都是用 curl 一条条打出来的，不是"我觉得应该没问题"。

### 亮点 2｜自研数据访问方言层：一套 SQL 跑三种数据库

**（简单介绍项目）** 还是百灵医生这个项目，我是唯一的开发，后端所有数据访问都归我，从建表、写 SQL 到部署全流程一个人做。

**（应用场景，引出我们要介绍的亮点）** 这个项目一开始是 SQLite，因为我希望它"拷走就能跑"，评审老师或者面试官拿到代码不用装数据库；但交付环境要求 MySQL 8，历史上我还想保留 PostgreSQL 的可能性。麻烦在于三种库的占位符、自增写法、取新主键的方式、列类型、事务开启语句、索引幂等语法全都不一样，如果每个接口都写三种分支，那我改一个字段要改三处，迟早出错。

**（技术选型）** 开发前我对比了三种方案。方案一是直接上 SQLAlchemy 加 Alembic，好处是成熟、迁移版本化、换库基本免费，坏处是这一版我想把 SQL 练明白，ORM 生成的语句对我是黑盒，出问题不好查；方案二是在业务代码里按引擎写 if/else，好处是直观、改动小，坏处是同一个查询要维护三份，而且分支会渗透到每个接口；方案三是自研一层方言层，只对 SQL 文本做重写，业务层永远只写一种 SQL，坏处是这层代码要自己写、边界要自己踩。

**（最终选择 + 为什么）** 我选了方案三，把差异全部收敛到 db.py 一个文件里。理由是这个项目要的是"业务代码零方言"，而不是"我支持三种数据库"这个标签——只要业务层里还能看到一处 %s 或者 AUTO_INCREMENT，这个目标就没达成。后面也确实证明，最难的不是写转换，而是踩出那些只有真跑起来才会暴露的限制。

**（实现步骤）** 第一，占位符统一写 ? ，进方言层后翻译成 %s；第二，建表 DDL 做重写：AUTOINCREMENT 转 AUTO_INCREMENT 或 SERIAL，TEXT、REAL、BLOB 按引擎映射成 VARCHAR(n)、DOUBLE、MEDIUMBLOB；第三，取新主键分派，SQLite 和 MySQL 走 lastrowid，PostgreSQL 走 RETURNING；第四，事务开启从 BEGIN IMMEDIATE 换成 START TRANSACTION，并封装成 db.tx() 上下文管理器；第五，索引创建做成幂等。

**（深度优化/问题解决）**

场景一：MySQL 直接建表就失败，因为它不允许在 TEXT 列上建索引和唯一约束。
解决方案：在建表 DDL 转换阶段做类型窄化——凡是要进索引或唯一约束的 TEXT 列，统一映射成 VARCHAR(n)，长度按业务语义定，比如手机号就给固定长度。这不是语法转换，是语义转换，所以必须放在 DDL 层而不是 SQL 层。

场景二：CREATE INDEX IF NOT EXISTS 在 MySQL 8 上是语法错误，但 SQLite 和 PG 都支持。
解决方案：改成先查 information_schema.statistics 判断索引是否存在，存在就跳过；同时兜住 1061（索引已存在）这个错误码，防止并发启动时两个人一起建。

场景三：查表结构的方法在两边完全不一样。
解决方案：db.columns() 内部做分派，SQLite 走 PRAGMA table_info，MySQL 和 PG 查 information_schema.columns，对外统一成一种结构，上层补列逻辑只写一遍。

**（对了，我再补充一点）** 迁移过程中还发现两个隐性问题：一是 REAL 在 MySQL 里对应 DOUBLE，不映射会精度不一致；二是 users.phone 原来是 TEXT，要建唯一索引就必须变成 VARCHAR——这些都不是"看起来对不对"，是跑一遍才报出来的。所以我的结论是：方言层这种活，靠读文档写不出来，只能靠一次次切库跑通。

**（最终结果）** 现在切库只改 DATABASE_URL 一行重启就行；切换后我逐表核对了行数，20 张表一致，全量接口回归通过，36 项测试跑通；方言层本身只有 567 行，代价可控。我也说清边界：这不是 ORM，没有版本化迁移，真实项目我会直接用 SQLAlchemy 加 Alembic。

### 亮点 3｜资金与库存的正确性：事务化下单支付 + 防超卖 + 退款回补

**（简单介绍项目）** 百灵医生里的商城是我从零写的，下单、支付、退款、库存、优惠券这条资金链路全部由我负责，后端接口 76 个里有 10 个是订单域的。

**（应用场景，引出我们要介绍的亮点）** 自测的时候我拿手机连点了两下支付按钮，结果出来两条扣款记录、优惠券被核销了两次；还有一次我把库存字段加上之前，一个售罄的商品能被无限下单。另外下单和支付原来是多条独立的 UPDATE，中间抛异常就会留下"订单已付、券没核销、库存没扣"的脏数据。这三个问题都不是功能缺失，是**数据正确性**问题，在电商里就是事故，所以我把这一段当成整个项目最需要打磨的地方。

**（技术选型）** 开发前我对比了三种方案。方案一是应用层加锁，比如 Python 的线程锁或者分布式锁，好处是写起来直观，坏处是单进程有效、多 worker 就失效，而且锁的粒度不好控；方案二是悲观锁，SELECT … FOR UPDATE 把行锁住再算，好处是语义最清晰，坏处是多一次往返，而且 SQLite 根本不支持 FOR UPDATE，我前面的三库兼容就白做了；方案三是条件更新加统一事务边界，把判断写进 WHERE 里，靠数据库的原子性保证正确。

**（最终选择 + 为什么）** 我选了方案三。因为 UPDATE … WHERE stock>=? 本身就是一次原子的比较并交换（CAS），本来就是数据库最擅长的事，不需要我再加一层锁；而且它在 SQLite、MySQL、PostgreSQL 上行为一致，正好接上我的方言层。缺点是 rowcount 必须真的去判断，不判断等于白写。

**（实现步骤）** 第一，用 db.tx() 上下文管理器统一事务边界，进入开事务、异常整体 ROLLBACK、正常 COMMIT，并把 rowcount 暴露出来；第二，下单和支付放进同一个事务，扣库存用 UPDATE meds SET stock=stock-?, sales=sales+? WHERE id=? AND stock>=?，rowcount 为 0 说明被别人抢先扣完了，直接抛错整体回滚；第三，支付的状态迁移带上 status='待支付' 这个条件，rowcount 为 0 就当成"已经处理过"，直接返回提示；第四，退款做成闭环：状态迁移、库存回补、销量回退、写通知，全在一个事务里。

**（深度优化/问题解决）**

场景一：用户双击支付按钮，重复扣款、重复核销优惠券。
解决方案：把幂等做进状态迁移里，UPDATE orders SET status='已支付' WHERE id=? AND status='待支付'，第二次请求 rowcount 是 0，直接返回"该订单已处理"，天然挡住重复提交，不需要前端禁用按钮这种不可靠的做法。

场景二：退款回补把"不限库存"的商品变成了有库存。
解决方案：stock 为 NULL 表示不限库存，退款时用 CASE WHEN 判断，NULL 就保持 NULL 不回补，否则会把一个无限量商品变成限量商品，这是数据语义错误，比功能错误更难发现。

**（对了，我再补充一点）** 有人会问为什么不用 SELECT FOR UPDATE，我的回答是：条件更新少一次网络往返，而且它的正确性来自数据库的原子性，不依赖隔离级别配置；代价是失败要自己判断 rowcount，且业务如果复杂到需要读多行再统一决策，那还是得用悲观锁。我不想把"没用锁"说成优点，它只是在这个场景下更合适。

**（最终结果）** 并发双请求支付同一订单，只有 1 次成功；库存不会为负、销量只加 1；退款后库存精确回补、销量不跌破 0。这些不是我口头保证，是 test_stock.py 里的并发用例跑出来的结论，现场可以执行给你看。

### 亮点 4｜读性能：全量拉取改分页 + 复合索引 + EXPLAIN 验证

**（简单介绍项目）** 百灵医生后端 76 个接口里，列表类接口是最多的，订单、消息、医生、优惠券、地址都要列表，这部分优化也是我一个人做的。

**（应用场景，引出我们要介绍的亮点）** 早期所有列表接口都是全量 SELECT、没有 LIMIT。订单多起来以后，我的订单页一次渲染出来的内容有 6519 像素高，手机上直接卡；而且没有索引的时候 EXPLAIN 出来全是 SCAN TABLE 全表扫。用户感知是"这个 App 好卡"，本质是接口设计没做分页、数据库没有索引。

**（技术选型）** 开发前我对比了三种方案。方案一是在前端做虚拟滚动加懒加载，好处是后端不用改，坏处是数据全量还是从服务端搬过来了，首屏依然慢，治标不治本；方案二是服务端 offset 分页，好处是实现简单、支持跳页、前端改动小，坏处是深翻页要扫过前面所有行；方案三是 keyset 游标分页，好处是深翻页恒定快，坏处是不能跳页、要维护游标，前端交互要重写。

**（最终选择 + 为什么）** 我选方案二，并配套建复合索引。因为这个项目的数据量是几百到几千条级，offset 完全够用，而跳页、按状态筛选这些交互体验更重要；方案三的成本在这个量级属于过度设计。但我把演进方向说清楚：如果数据上百万，就必须换 keyset，WHERE id < last_id 那种写法，这一点我在文档里也登记了。

**（实现步骤）** 第一，抽一个 paging() 统一处理入参：limit 默认 20、夹紧在 1~100，offset 负数归 0，避免调用方传 limit=99999 打爆数据库；第二，响应体统一追加 total、limit、offset、has_more 四个字段，前端只看 has_more 决定要不要继续拉；第三，前端列表首屏 limit=20，加载更多是追加而不是覆盖；第四，建 11 个复合索引，严格对齐查询条件顺序；第五，用 EXPLAIN QUERY PLAN 逐条验证索引是否命中。

**（深度优化/问题解决）**

场景一：分页做完了，但前端还在本地按状态过滤，导致某个状态的订单落在还没翻到的页外面，用户以为没有订单。
解决方案：把所有状态筛选挪到后端，列表接口带 status 条件查询，前端只负责取数和渲染。这个坑很典型——分页不只是加 LIMIT，凡是"前端全量再过滤"的地方都得一起改。

场景二：复合索引的列顺序到底谁在前。
解决方案：按区分度排。比如"我的订单按状态查"，索引建成 (user_id, status) 而不是 (status, user_id)——user_id 先把结果集砍到个位数，status 再做二次过滤；反过来 status 只有几个枚举值，几乎不筛，索引就废了。

**（对了，我再补充一点）** 我还顺手改了一个统计问题：我的页面上的数字原来是前端拉全量再算，分页之后这么算一定是错的，所以改成后端聚合返回。这类"分页引发的连锁修改"最容易漏，我把它当成一次专项收尾来做。

**（最终结果）** EXPLAIN 从 SCAN TABLE 变成 SEARCH … USING INDEX，11 个复合索引逐条验过；列表接口统一返回四字段分页结构；订单页不再一次性渲染几千像素。证据是 EXPLAIN 的输出和接口返回，现场可以直接看。

### 亮点 5｜安全横切层：不是"写了"，是"实测生效"

**（简单介绍项目）** 这个项目的横切能力——日志、限流、异常处理、安全头——都是我单独抽一层写的，放在 core.py 里，249 行。

**（应用场景，引出我们要介绍的亮点）** 我做自查的时候发现两个现象：一是响应头里根本没有 CSP、nosniff 这些安全头，浏览器层面等于一点防护都没有；二是上传接口只校验扩展名，我传一个改名的 .html 上去，它能被当静态页打开，等于给自己开了个 XSS 的洞。这两条在演示里毫无感觉，但一旦上线就是真问题。

**（技术选型）** 开发前我对比了三种做法。方案一是在 Nginx 层统一加头，好处是不占应用性能、运维改一处就行，坏处是本地开发环境不生效，而且配置容易漂移，我改代码看不见效果；方案二是在应用里用中间件统一注入，好处是开发和线上一致、随代码走、可测试，坏处是每个请求都要过一次；方案三是每个接口里各自加，好处是最灵活，坏处是漏一个就等于没做。

**（最终选择 + 为什么）** 我选方案二，写成 core.harden() 统一注入。原因是"安全"这件事最怕的就是"以为做了"——我要的是所有响应路径（包括异常响应）都带上，只有统一的出口才能保证这一点；性能上一次函数调用可以忽略。

**（实现步骤）** 第一，harden() 统一注入 Content-Security-Policy、X-Content-Type-Options: nosniff、X-Frame-Options，并做 CORS 白名单；第二，限流写成滑动窗口，按 IP 和手机号双维度分桶，超限返回 429，带 sweep 惰性清理避免内存无限涨；第三，上传加固做四道：扩展名白名单、magic number 文件头校验、5MB 大小上限、拒绝路径穿越，静态托管时对非图片补 Content-Disposition；第四，统一异常处理器分三层（校验错误、HTTP 错误、未捕获异常），中文文案，不泄漏堆栈；第五，日志里手机号中间四位打码。

**（深度优化/问题解决）**

场景一：安全头的代码明明写了，响应里却查不到。
解决方案：不猜，直接打真实请求把响应头打出来逐项比对，最后定位到中间件没有真正注册到应用上。这件事对我是个教训——代码存在不等于能力存在，所以之后我给所有横切能力都加了"实测生效"这个验收项。

场景二：改完限流之后，我自己连续跑测试被拦成了 429，测试直接红。
解决方案：确认是限流真的生效之后，改成等窗口过期再跑回归；同时把这个现象写进报告，因为它反过来证明了限流没写错。这里我也如实说明局限：内存版多 worker 或重启之后不共享计数，生产必须换 Redis。

**（对了，我再补充一点）** 限流为什么还要按手机号分桶？因为短信验证码接口真正的攻击面是"刷某一个手机号"，只按 IP 拦不住代理池，代理池每个 IP 都是新的。这个细节是我做威胁分析的时候想明白的，不是照抄配置。

**（最终结果）** CSP、nosniff、X-Frame-Options 实测出现在响应头里；伪装成图片的 HTML 上传被拒；超限请求稳定返回 429。这三条都能现场用一条 curl 看到，不需要看我的代码。

### 亮点 6｜AI 能力：自研极简 RAG + SSE 流式，且能优雅降级

**（简单介绍项目）** 百灵医生里的 AI 预问诊是我做的，包括知识库、检索、流式对话和前端打字机效果，rag.py 309 行全是自己写的。

**（应用场景，引出我们要介绍的亮点）** 医疗场景里最不能接受的是"编"。如果直接把用户症状丢给大模型问"我该吃什么药"，它会给你一个听起来很专业但没有出处的建议，这在医疗里是不能接受的。所以我需要的不是"接个 API"，而是让回答能溯源到具体文档；另外如果等模型生成完再返回，用户要盯着屏幕等十几秒，看起来像卡死。

**（技术选型）** 开发前我对比了三种方案。方案一是直接拼 prompt 调大模型，好处是一天能上线，坏处是无依据、不可溯源、模型一换答案就漂；方案二是上 LangChain 甚至向量数据库全家桶，好处是功能齐全、别人问起来"用过什么框架"好答，坏处是依赖重、链路是黑盒，被追问哪一步做了什么我答不上来，而且千级数据量用向量库是杀鸡用牛刀；方案三是自研一条极简 RAG，好处是三百行以内、每一步我都讲得清、能按需降级，坏处是没有现成的评测体系，要自己做可观测。

**（最终选择 + 为什么）** 我选方案三。判断标准很简单：这个项目的价值在于我真懂这条链路，而不是我在配置文件里填了一个框架名。向量库我明确不做——片段是千级，纯 Python 暴力点积就是毫秒级，引入 FAISS 或 Milvus 属于过度设计；但我把检索函数抽成 search()，量级上来只换这一个函数。

**（实现步骤）** 第一，split_text 做带重叠的分块，避免一句话被切断在两块里；第二，embed 做双通道，优先调远端 embedding 接口，不可用时退化成确定性的本地哈希向量；第三，向量用 BLOB 打包存库，检索时还原后做点积，取 Top-K 并用 min_score 阈值过滤；第四，build_context 把召回片段拼成带出处的上下文再交给大模型，回答可溯源；第五，对话走 SSE，自定义 meta、delta、done、error 四种帧，前端逐帧渲染打字机。

**（深度优化/问题解决）**

场景一：在没有外网、没有 API Key 的机器上演示，AI 功能直接不可用。
解决方案：双通道 embedding 加规则兜底——远端不可达就退成本地哈希向量，还没有 Key 就走本地规则应答，保证 clone 下来 run 起来 AI 这块有完整流程可看。两条通道的产物可以共存，切回来不影响已有向量。

场景二：流式输出如果实现得不好，用户还是等十几秒。
解决方案：SSE 用 text/event-stream，先发 meta 帧把会话信息推给前端，之后每个 delta 帧一有内容就推，前端边收边渲染；相比轮询延迟低，相比 WebSocket 不用双工和额外握手。中间任何一步出错就发 error 帧，前端有明确的失败态而不是一直转圈。

**（对了，我再补充一点）** 我专门留了三个运维接口：/api/rag/status 看知识库和向量库的自检状态，/api/rag/search 直接看召回结果，/api/rag/rebuild 重建索引。原因是我没法像评测模型那样评 RAG，那至少要让召回过程可观测——出问题时我能一眼看出是没检索到，还是检索到了但模型答歪了。

**（最终结果）** 知识库 8 篇按科室组织的医疗科普，48 个片段完成向量化；/api/rag/search 能看到召回片段和分数；对话是逐帧流式返回，首帧即回，不用等整段生成；没有 Key 的环境走规则兜底依然能演示完整链路。

### 亮点 7｜业务真实感：不臆造未发生的状态

**（简单介绍项目）** 百灵医生的前端 32 个页面也是我写的，订单、处方、评价这些业务细节的打磨都在这部分。

**（应用场景，引出我们要介绍的亮点）** 演示的时候被指出两个问题：一是连续点两个不同商品，详情页显示的是同一个商品；二是一个还没发货的订单，物流时间轴上却出现了"已签收"。第一个是前端缺陷，第二个是更严重的问题——我在"编造"系统里根本没发生的事。做业务系统，数据可以少，但不能假。

**（技术选型）** 针对详情页串数据这个问题我对比了三种改法。方案一是把数据放到 Pinia 里缓存，好处是切换快，坏处是要维护缓存失效，一旦 invalidation 写错就是更隐蔽的串数据；方案二是在组件内统一 load()、onMounted 加 watch(route.params)，好处是精准、成本最低，坏处是每个详情页都要照这个模板写一遍；方案三是给 router-view 加 key 强制重建组件，好处是一行代码解决，坏处是整页重建、丢滚动位置、性能差。

**（最终选择 + 为什么）** 我选方案二。因为问题根因是同一个组件实例被复用、onMounted 只跑了一次，那就应该在参数变化时重新取数，而不是靠缓存或者销毁重建去绕过它。方案三看起来最省事，其实是把"数据不对"换成了"体验变差"，问题没解决。

**（实现步骤）** 第一，所有按路由参数取数的详情页统一成 load() + onMounted(load) + watch(route.params) 三件套；第二，订单对外单号用 BL 加下单日期加 6 位序号，和内部自增 id 解耦，运单号按 id 稳定推导，刷新不变；第三，物流时间轴严格由 created、pay_time、ship_time、finish_time 四个真实字段生成，没发货就不显示物流节点；第四，评价加 UNIQUE(order_id, med_id, user_id) 约束，并且只允许已完成订单评价；第五，软删除四处口径同步。

**（深度优化/问题解决）**

场景一：一单能重复评价，并发提交还能写进两条。
解决方案：库层唯一约束加状态闸门双保险——前端和后端都校验"仅已完成订单可评"，但真正兜底的是那个唯一索引，并发下第二条根本插不进去，抓到冲突就返回中文提示。我的原则是：能用约束保证的，不要靠判断保证。

场景二：订单改成软删之后，列表里没了，但直接打开详情还能看到。
解决方案：把列表、total、我的页面统计、详情接口这四处的过滤条件一起改，越权、已删、不存在统一返回 404，不泄漏资源到底存不存在。这类"改一处忘了另外三处"是软删最常见的坑。

**（对了，我再补充一点）** 为什么订单不硬删？订单是资金凭证，详情页和评价链路都要能回查，软删加全口径过滤是电商的通用做法；但通知这种没有下游引用的数据我直接硬删，不留垃圾。删得干不干净，取决于这个实体有没有被别处引用。

**（最终结果）** 连点两个商品不再串数据；未发货订单不会再出现签收节点；重复评价被拦下有明确提示；已删订单在四处口径统一 404。这些都是我自测时一条条点出来的问题，也是我改完后重新点一遍验证过的。

### 亮点 8｜质量体系：6 套测试 + 每轮改造都有自测报告

**（简单介绍项目）** 整个项目只有我一个人，所以质量和开发都得我自己兜；这部分讲的是我怎么保证"改一处不崩另一处"。

**（应用场景，引出我们要介绍的亮点）** 我改完库存逻辑，手动点了一遍下单支付，看起来都对，结果第二天试退款的时候发现库存回补错了——因为我根本没测那条路径。项目越到后期接口越多，手动点页面的成本越高、漏得越多，我就决定必须上自动化测试，而且要能一条命令跑完。

**（技术选型）** 我对比了三种方案。方案一是 pytest 加 requests，好处是生态好、断言方便、报告漂亮，坏处是要装依赖，换台机器或者评审环境里先得 pip install；方案二是标准库 unittest 加 urllib，好处是零第三方依赖、任何装了 Python 的机器都能跑，坏处是写起来啰嗦、没有现成的 fixture；方案三是用 Postman 集合手工点，好处是最直观，坏处是不能回归、不能进流程。

**（最终选择 + 为什么）** 我选方案二。因为我的目标受众是"拿到代码就想验证一下的人"，如果验证之前还要先配环境，那这套测试基本不会被跑；零依赖换来的啰嗦我能接受。

**（实现步骤）** 第一，按域拆成 6 个文件：test_api 覆盖主流程冒烟，test_tier1 覆盖鉴权、分页字段、索引命中、安全头这些基础设施，test_stock 覆盖库存与防超卖，test_review 覆盖评价，test_order_flow 覆盖订单链路，run_all 负责编排；第二，run_all.py 自己起服务、跑完自动关服务，一条命令出结果；第三，用例专门覆盖并发、越权、重复提交、422 越界这些容易漏的分支；第四，每轮改造在 docs 下留一份自测报告，固定写"改了什么、怎么验、结论、遗留风险"。

**（深度优化/问题解决）**

场景一：测试跑完把演示数据弄脏了，演示账号的优惠券被用掉，第二天演示直接不对。
解决方案：定纪律——测试数据必须物理清理，演示账号和演示订单不可动；涉及优惠券额度的验证，一律新注册随机手机号的用户来跑，不去消耗演示账号的额度。

场景二：连续跑两遍测试，第二遍全部 429 失败。
解决方案：确认是限流窗口还在，等窗口过期再跑；同时把这个现象登记进报告，说明它是限流的正确行为，而不是测试不稳定。这件事让我意识到，测试失败不一定是代码错，也可能是策略生效了，得先分清。

**（对了，我再补充一点）** 报告格式我是强制固定的四段：改了什么、怎么验、结论、遗留风险。特别是最后那段"遗留风险"，我不允许自己写"无"——每轮改造一定有没覆盖到的地方，写出来才叫工程记录，否则就只是交差。

**（最终结果）** 6 套测试全绿，一条命令 python tests/run_all.py 出结果，零第三方依赖；8 份自测报告可以按时间线回溯每一轮改造，面试官想看某一次改动怎么验的，我当场能翻出来。

### 亮点 9｜交付与运维：真的上线过，还更新过

**（简单介绍项目）** 项目做完不能只在我电脑上跑，交付和上线也是我做的，包括容器化、服务器部署、重复部署脚本和文档。

**（应用场景，引出我们要介绍的亮点）** 第一次上线我是手工敲命令：装 conda 环境、配 systemd、配 Nginx，敲了半小时还漏了环境变量。第二次迭代要更新代码的时候我犯难了——手工再敲一遍，一是慢，二是万一覆盖错了连回滚都没有。所以我必须把"部署"这件事变成脚本，而不是靠记忆。

**（技术选型）** 我对比了三种做法。方案一就是本地 python app.py 跑通交付，好处是零成本，坏处是那不叫交付；方案二是 Docker 加 compose，好处是环境一致、一条命令起服务，坏处是目标机是 CentOS7、docker 受限，而且数据库和 .env 的挂载还要额外处理；方案三是沿用机器已有的 conda 环境，用 systemd 托管 uvicorn，加 Nginx 反代，再写一个部署脚本，好处是和目标机现状贴合、可控、能回滚，坏处是要处理 shell 层面的坑。

**（最终选择 + 为什么）** 我选方案三，同时把 Dockerfile 和 compose 也留着作为交付备选。理由很现实：上线要以目标机现有条件为准，不能为了用某个工具去改造环境；而 Docker 那套的价值在于"别人拿到项目能一键起"，两个场景不冲突。

**（实现步骤）** 第一，本地 tar 打包，排除 .env、uploads、logs、node_modules，避免把密钥和运行数据推上去；第二，scp 上传到服务器；第三，远端自动备份上一版目录，出问题能立刻回退；第四，覆盖解压、pip install、systemctl restart；第五，curl 健康检查，确认接口真的活着才算部署成功。

**（深度优化/问题解决）**

场景一：部署脚本在本地一直中断，报 NativeCommandError。
解决方案：查出来是 PowerShell 调 ssh 时，首次连接的警告写进了 stderr，被当成原生命令错误抛出；改成 StrictHostKeyChecking=accept-new 加临时把 ErrorActionPreference 设成 Continue，再用 2>&1 过滤警告。这个坑跟业务无关，但不解决就上不了线。

场景二：手工执行 SQL 迁移，漏了一列，服务起来就报错。
解决方案：把迁移做进启动流程——init_schema 负责建表，MIGRATE_COLS 负责缺列自动补齐，加 stock、deleted、ship_time、express_no 这些列全是自动完成的，再不需要我上去敲 SQL。

**（对了，我再补充一点）** 因为有自动备份，重部署的中断时间能压到 3 秒左右——停服务、解压、重启这几步；我也如实说局限：这是单机部署，没有滚动发布、没有健康检查探针、没有灰度，真实生产要补这些。

**（最终结果）** 两次真实部署：首次上线和一次迭代更新，都能用 systemctl status 和日志核验；0 次手工 SQL；公网通过 Cloudflare 隧道可以访问演示；README 和 deploy 文档写清了从零部署的每一步。

### 4.5 三个 STAR 案例（各 60 秒，建议背下来）

**案例 A · 防超卖与重复支付**
- S：用户双击支付按钮，出现重复扣款、优惠券重复核销、库存为负。
- T：不引入分布式锁，也要保证"同一订单只成功一次、库存不为负"。
- A：`db.tx()` 统一事务边界；库存用 `UPDATE ... WHERE stock>=?` 条件更新，`rowcount==0` 即被抢先并整体回滚；支付状态迁移带 `status='待支付'` 条件，`rowcount==0` 直接返回"已处理"。
- R：并发双请求支付同一订单**仅 1 次成功**，库存不为负，销量只 +1；退款在同事务内精确回补库存与销量。

**案例 B · 一套 SQL 跑三种数据库**
- S：交付环境要 MySQL 8，本地要零依赖 SQLite，历史还留着 PostgreSQL 支持。
- T：业务代码一行不改，靠 `DATABASE_URL` 切换。
- A：方言重写引擎——占位符、自增、取主键、类型映射、事务开启、索引幂等全部在 `db.py` 内分派；MySQL 不允许 `TEXT` 建索引，就在 DDL 转换阶段窄化为 `VARCHAR(n)`。
- R：切库后逐表行数一致、全量接口回归通过；`db.py` 仅 567 行，代价可控。

**案例 C · "代码写了，但没生效"**
- S：安全响应头代码存在，实际响应里却查不到。
- T：定位到底是没挂载、被覆盖，还是顺序问题。
- A：用真实请求打印响应头逐项比对，发现中间件未真正注册到应用。
- R：修复后 CSP / nosniff / X-Frame-Options 实测出现在响应头；此后所有横切能力都加"实测生效"验收项——**这条经验比功能本身更值钱**。

### 4.6 三句"反脆弱"表达（比自夸更有说服力）

1. **三句式**：「这块我做到了 X，边界是 Y，生产要补 Z。」——例：限流做到了按 IP+手机号分桶、超限 429；边界是内存版多 worker 不共享；生产要换 Redis。
2. **数字＋验法**：「76 个接口，你现在 grep 就能数出来。」——任何数字后面跟一句怎么验。
3. **失败收尾**：「这个项目里我修过两个自己造的问题：安全头没挂上、限流把测试拦成 429。」——主动暴露瑕疵，反而让其余结论更可信。

## 5. 讲述脚本

### 5.1 三分钟版（自我介绍里的项目段）

> "我做了一个在线问诊 + 医药电商的移动端应用，叫百灵医生。后端 FastAPI 单体 76 个接口、20 张表，前端 Vue3 + Vant 32 个页面，从墨刀原型一路做完，最后部署在 CentOS7 上用 systemd 跑起来。
> 我重点打磨了三件事：
> 第一是**安全边界**——手写 JWT，加了 token 版本号做撤销，登出后旧 token 立即失效；密码用 PBKDF2 二十万次迭代加随机盐，老数据登录时惰性升级；再加上滑动窗口限流、上传文件头校验和安全响应头。
> 第二是**数据正确性**——下单和支付放在同一个事务里，库存用条件更新做原子扣减，双击支付只会成功一次，退款时库存和销量在同事务内精确回补。
> 第三是**可扩展的数据层**——我自己写了一层方言抽象，同一份 SQL 能跑 SQLite、MySQL 8 和 PostgreSQL，切库只改一行配置；踩过 MySQL 不能在 TEXT 列建索引、`CREATE INDEX IF NOT EXISTS` 不支持这些坑。
> 另外接了通义千问做 AI 预问诊，自己实现了 RAG 的完整链路，包括双通道 embedding 降级和 SSE 流式输出。整个项目有 6 套自动化测试，每轮改造都留了自测报告。"

### 5.2 八分钟版（深挖顺序）

1. **业务全景 1 分钟**：画上面那条闭环链，强调"一条能走通的链"而非散点功能。
2. **架构与分层 1 分钟**：`app.py` / `core.py` / `db.py` / `schemas.py` / `rag.py` 五文件职责，横切下沉。
3. **亮点 1 鉴权 1.5 分钟**：token_ver 撤销 + 密码惰性升级。
4. **亮点 3 事务与库存 2 分钟**：条件更新 CAS + 幂等 + 退款回补，讲清"为什么不会超卖"。
5. **亮点 2/4 数据层与性能 1.5 分钟**：方言层三个拦路虎 + 分页四字段 + 索引列顺序理由。
6. **亮点 6 AI 1 分钟**：RAG 五步 + 降级策略。

| 为什么单体不用微服务？ | 个人项目、单机部署，微服务只会带来分布式事务与运维成本；我把横切层下沉、数据访问收敛，保留了将来拆分的能力 |

| JWT 存 localStorage 有 XSS 风险吗？ | 有；生产建议 HttpOnly + SameSite Cookie + CSRF token，本项目已加 CSP 与上传白名单做缓解，属已知取舍 |
| 事务怎么保证一致？ | `db.tx()` 上下文管理器，异常整体回滚；关键更新带状态条件 + `rowcount` 判定，兼顾幂等 |
| 分页 offset 大了会慢吗？ | 会；深分页应改 keyset（`WHERE id < last_id`）游标分页，本项目数据量级用 offset 足够 |
| 索引是不是越多越好？ | 不是；写放大与存储成本，只为高频过滤列建，并保持复合索引列顺序与查询一致 |
| RAG 效果怎么评估？ | 目前用 `min_score` 阈值 + 人工抽检 + `/api/rag/search` 可观测召回；生产应补 recall@k 与答案忠实度评测 |
| embedding 为什么做双通道？ | 保证无网/无 Key 环境可演示，且远端与本地通道产物可共存，切换不影响已有向量 |
| 限流怎么在多实例生效？ | 现在内存桶只单进程有效，生产换 Redis + 滑动窗口（ZSET 或固定窗口 + 原子 INCR） |
