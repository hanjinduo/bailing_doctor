## 二、后端设计

### 2.1 数据表

```sql
CREATE TABLE reviews (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  med_id INTEGER NOT NULL,
  user_id INTEGER NOT NULL,
  order_id INTEGER NOT NULL,
  rating INTEGER NOT NULL,        -- 1~5
  content TEXT DEFAULT '',
  anon INTEGER DEFAULT 0,         -- 1=匿名
  deleted INTEGER DEFAULT 0,
  created TEXT
);
CREATE INDEX idx_reviews_med ON reviews(med_id);
CREATE UNIQUE INDEX idx_reviews_once ON reviews(order_id, med_id, user_id);
```

- 唯一索引 `(order_id, med_id, user_id)` 在库层面兜住"同一单同一商品只能评一次"，并发重复提交不会写出脏数据。
- 表结构与索引均并入 `SCHEMA`，MySQL 方言由 `db.py` 的 `ddl_for()` 转换（TEXT 索引列窄化为 VARCHAR）。

### 2.2 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/order/{oid}/review` | 发表评价，需登录且订单属于本人 |
| GET | `/api/meds/{mid}/reviews` | 评价列表，匿名可访问，分页，附统计 |
| GET | `/api/meds` | 列表项新增 `rating` / `review_count` |
| GET | `/api/meds/{mid}` | 详情新增 `rating` / `review_count` |
| GET | `/api/order/{oid}` | 商品项回显 `reviewed`，顶层回显 `can_review` |

**发表评价的业务校验（全部返回中文提示）**

1. 订单不存在 / 非本人订单 → 拒绝（越权统一 404 语义）。
2. 订单状态必须为「已完成」→ 待支付/待发货/已发货一律拒绝。
3. 评价商品必须在该订单明细内 → 否则拒绝。
4. 该商品在该订单下已评价过 → 拒绝。
5. `rating` 越界（<1 或 >5）→ Pydantic 返回 422。

**统计口径**：`avg` 均分保留一位小数、`count` 总条数、`good_rate` 好评率（4~5 星占比，整数百分比）、`dist` 五档星级分布；昵称统一脱敏（首字 + `**`），匿名评价对外显示「匿名用户」。

## 七、已知边界

1. 评价不支持追评、图片上传、商家回复；星级仅整数，无半星。
2. 评价不可修改与删除（唯一索引保证一单一评），若后续需要「改评价」应改为更新语义而非新增行。
3. 均分为实时聚合查询，商品列表页每页都会按 `med_id` 做两次聚合；商品量上千后建议加 `meds.rating` / `meds.review_count` 冗余列并在写入时更新。
4. 匿名仅影响对外展示，后台与本人仍可追溯，符合风控要求。
