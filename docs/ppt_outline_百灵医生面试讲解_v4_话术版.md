### 11 话术 1｜鉴权：不是验个签名，而是可撤销体系
- ① 简单介绍项目 · 我的职责：项目叫百灵医生，在线问诊加医药电商，76 个接口、20 张表、32 个页面。 / 后端全部接口和前端页面都是我一个人做的，鉴权这块也是我从零写的。
- ② 应用场景 · 为什么非做不可：自测时发现两件事：登出以后旧 token 还能访问 /api/me；改完密码，旧手机上的登录态照样有效。 / 在医疗场景里，这等于别人还能继续看你的问诊记录和处方，所以 token 必须能作废。
- ③ 技术选型 · 对比 3 种方案：① Session 存服务端：天然可撤销，但每个接口都要查会话，还得引入额外存储。 / ② 用现成 JWT 库：省事、标准化，但撤销仍要自己再挂一张黑名单表。 / ③ 手写 HS256 加版本号：多写几十行，撤销和密钥校验全在自己手里。
- ④ 最终选择 · 为什么是它：最后选③。因为我真正要解决的是能不能失效，撤销既然得自己写，不如把签发一起写掉。 / 代价我也清楚：得自己实现常量时间比较、写死算法、每个请求多一次主键查询。
- ⑤ 实现步骤 1 / 2 / 3：一、手写 HS256 签发与校验，密钥从环境变量到 .env 逐级读取，短于 32 位直接拒绝启动。 / 二、users 表加 token_ver 并写进载荷比对，登出、改密时自增，旧 token 立即失效。 / 三、补 /api/logout 接口；密码从 sha256 换成 PBKDF2，20 万次迭代加每用户随机盐。
- ⑥ 问题场景 → 解决方案：场景一：改密以后旧 token 仍然有效。 / 解决方案：靠 token_ver 比对，版本不一致直接 401，不维护黑名单。 / 场景二：老库里存的是旧哈希，换算法会全员登不上。 / 解决方案：登录成功后再算 PBKDF2 覆盖，惰性迁移，不停机。
- ⑦ 对了，再补充一点：为什么不用现成库：六十行业务代码就够用，绕它的扩展点反而更贵；token_ver 每请求一次主键查的开销我知道，真上生产换 Redis 缓存。
- ⑧ 最终结果 · 量化指标：伪造签名 401；登出后旧 token 访问 /api/me 返回 401；跨用户读订单 404。 / 这三条都是 curl 一条条打出来的，不是“应该没问题”。

### 12 话术 2｜自研方言层：一套 SQL 跑三种数据库
- ① 简单介绍项目 · 我的职责：项目后端一开始直连 SQLite，零依赖好跑；但交付要上 MySQL 8，我自己还留了 PostgreSQL 做对比。 / 数据访问层 567 行是我一个人重写的。
- ② 应用场景 · 为什么非做不可：同一份代码，三套数据库语法：占位符、自增写法、取主键的结果都不一样。 / 换一次库就得维护三套代码，同事接手第一句话是问“这段 SQL 是哪个库的”。
- ③ 技术选型 · 对比 3 种方案：① 直接上 SQLAlchemy：成熟生态，但它自动生成的 SQL 我看不到细节。 / ② 只支持 SQLite，交付时手工改：改动最小，但每次部署都要人工过一遍。 / ③ 自研薄方言层：多花两天，业务只写一种 SQL。
- ④ 最终选择 · 为什么是它：选③。这是我要讲清楚的项目，我更想要看得见的 SQL；而且手改试过，一次漏改就是启动报错。 / ORM 的版本化迁移能力我确实没有，后面靠启动时列自动补齐来兜。
- ⑤ 实现步骤 1 / 2 / 3：一、把三库差异收敛到 db.py：占位符 ? 与 %s、自增写法、取主键方式三处适配。 / 二、封装 db.tx() 事务上下文，以及 columns() / indexes() 元数据分派。 / 三、建表、索引、分页等公共语法抽成一处，业务层零方言。
- ⑥ 问题场景 → 解决方案：场景一：MySQL 不允许 TEXT 列直接建索引。 / 解决方案：DDL 里把被索引的列窄化成 VARCHAR。 / 场景二：MySQL 8 不支持 CREATE INDEX IF NOT EXISTS，启动直接报错。 / 解决方案：先查 information_schema 判断索引是否已存在，再决定建不建。
- ⑦ 对了，再补充一点：这套东西的价值不在“支持三库”这句说法，而在于切库那天我只改了一行 DATABASE_URL，逐表行数对得上、全量接口回归通过。
- ⑧ 最终结果 · 量化指标：方言层 567 行；改一行配置切三库；切换后逐表行数一致、76 个接口回归通过。

### 13 话术 3｜资金与库存正确性：事务化 + 防超卖 + 退款回补
- ① 简单介绍项目 · 我的职责：商城侧要真的有库存和钱：下单、支付、取消、退款都得算对。 / 这条链路的接口和事务边界是我写的。
- ② 应用场景 · 为什么非做不可：自测时发现三个真问题：订单和多条明细各自 UPDATE，中途失败留下半张脏单；支付按钮连点两次扣两次钱；药品表压根没有库存字段，能无限下单。 / 在医药电商里，这三条都是资金和库存事故。
- ③ 技术选型 · 对比 3 种方案：① 每条 UPDATE 各自提交：最简单，但没法整体回滚。 / ② SELECT 加 FOR UPDATE 行锁：稳妥，但三库语法各异、还依赖隔离级别。 / ③ 事务上下文加条件更新 CAS：一次往返，三库通用。
- ④ 最终选择 · 为什么是它：选③。条件更新把“判断”和“扣减”合成一条 SQL，原子性交给数据库； / 事务上下文保证一张单要么全成、要么全滚。
- ⑤ 实现步骤 1 / 2 / 3：一、写 db.tx() 上下文管理器，异常整体 ROLLBACK，统一暴露 rowcount。 / 二、扣库存用 UPDATE meds SET stock=stock-?, sales=sales+? WHERE id=? AND stock>=?。 / 三、支付状态迁移带 status=待支付 条件，rowcount 为 0 就直接返回“已处理”。
- ⑥ 问题场景 → 解决方案：场景一：双击支付重复扣款。 / 解决方案：迁移条件限定“待支付”，第二次 rowcount 为 0，幂等返回。 / 场景二：取消或退款后库存不回。 / 解决方案：状态迁移、库存回补、销量回退、写通知，同一个事务里完成。
- ⑦ 对了，再补充一点：补充一点：退款不是简单把库存加回去，还要把销量减回来、给用户写通知，这三件事必须同事务，否则对账一定乱。
- ⑧ 最终结果 · 量化指标：并发两个请求只有 1 次成功；库存从不为负；销量只加 1；退款精确回补。 / 用的是 tests/test_stock.py，现场能跑。

### 14 话术 4｜读性能：统一分页 + 11 个复合索引
- ① 简单介绍项目 · 我的职责：项目 20 张表里，订单、问诊、通知这类列表最容易涨，数据一多页面就卡。 / 分页和索引这块是我统一收口的。
- ② 应用场景 · 为什么非做不可：上线前列表接口是全量返回，我的订单、优惠券、地址一次拉几百条，手机上明显白屏等。 / 真实用户数据只会更多，不分页就是埋雷。
- ③ 技术选型 · 对比 3 种方案：① 前端切片分页：改得快，但后端还是一次查全量，没解决根因。 / ② 后端 LIMIT / OFFSET 分页：标准做法，但要统一参数和返回结构。 / ③ key_set 游标：深分页最优，但改造面大、前端加载逻辑要重写。
- ④ 最终选择 · 为什么是它：选②，并且把三个细节定死：limit 默认 20 夹在 1 到 100、offset 负数归 0、返回统一带 total/limit/offset/has_more。 / 为什么不做③：当前数据量到不了深分页程度，那属于过度设计，先留口子。
- ⑤ 实现步骤 1 / 2 / 3：一、抽 paging() 和 page_meta() 两个函数，所有列表接口共用。 / 二、订单、通知、地址、优惠券、医生列表逐个接上，前端触底加载 PAGE 取 20。 / 三、按查询列序建 11 个复合索引，逐条 EXPLAIN 看执行计划。
- ⑥ 问题场景 → 解决方案：场景一：加索引前列表查询是 SCAN TABLE，全表扫。 / 解决方案：按区分度和过滤顺序建复合索引，比如 user_id 加 status，EXPLAIN 变成 SEARCH USING INDEX。 / 场景二：索引列序建反了，等于白建。 / 解决方案：对照 WHERE 和 ORDER BY 的列序重建，逐条复核执行计划。
- ⑦ 对了，再补充一点：补充一点：复合索引不是越多越好，列序错了就是白建；真到千万级，分页得换 key_set 游标，否则 OFFSET 越翻越慢。
- ⑧ 最终结果 · 量化指标：11 个复合索引；列表查询由全表扫变索引查；统一四字段分页返回；前端触底加载 20 条一页。

### 15 话术 5｜安全横切层：限流、上传校验、安全头
- ① 简单介绍项目 · 我的职责：这个项目要对外演示，等于挂在公网上，安全没法只靠“应该没事”。 / 限流、上传校验、安全响应头都是我补的。
- ② 应用场景 · 为什么非做不可：自测时三个问题：连着点验证码接口，服务把正常请求也拦了；上传只校验扩展名，改个后缀就能过；安全头代码明明写了，响应里却没有。 / 这三类上线就是漏洞。
- ③ 技术选型 · 对比 3 种方案：① 每个接口自己写判断：最直接，但一定会漏。 / ② 中间件统一收口：一次写完全局生效，但要小心把测试也拦住。 / ③ 上现成网关或框架插件：省事，但项目定位是零依赖单体。
- ④ 最终选择 · 为什么是它：选②。横切关注点全部下沉到 core.py，业务代码里不出现限流和响应头逻辑。 / 这是一个刻意的架构决定：业务只写业务。
- ⑤ 实现步骤 1 / 2 / 3：一、滑动窗口限流按 IP 加手机号分桶，超限返回 429，并加 sweep 惰性清理过期键。 / 二、上传做扩展名白名单、magic number 校验、5MB 上限、拒绝路径穿越。 / 三、harden() 统一注入 CSP、nosniff、X-Frame-Options。
- ⑥ 问题场景 → 解决方案：场景一：限流把测试自己拦成 429。 / 解决方案：规则按接口分档，短信 5 次、登录 10 次，留 300 兜底，测试用独立手机号。 / 场景二：安全头代码在，响应里没有。 / 解决方案：打印真实响应头，定位到中间件没挂上，修好后列入必验项。
