# 百灵医生 · 在线问诊 APP 技术说明（面试版）

> 本文档面向技术面试，目标不是罗列功能，而是把**每一个技术选型背后的判断、取舍与可验证数字**讲清楚。
> 全篇按「能被追问」的标准组织：每个专题都有 **为什么这么做 → 怎么实现 → 踩过什么坑 → 怎么验证 → 会被怎么追问**。

## 一、项目速览

| 项 | 内容 |
|---|---|
| 定位 | 移动端优先的在线问诊 + 医药电商一体化演示应用，可完成「选医生 → 付费问诊 → AI/医生对话 → 开处方 → 下单购药 → 订单管理」完整闭环 |

| 数据层 | SQLite / PostgreSQL **双栈**，统一经由 `db.py` 抽象，切换只改环境变量 |
| 前端 | Vue 3 + Vite + Vue Router + Pinia + Axios + Vant 4，**27 个页面组件**，构建产物由 FastAPI 直接托管 |
| AI 能力 | **RAG 知识库检索增强**（8 篇科室指南 / 48 个语义块）+ **SSE 流式输出**，无外部依赖自研实现 |
| 鉴权 | 手写 **HS256 JWT**（hmac + hashlib + base64，零第三方库） |
| 可靠性 | 结构化日志、统一异常、滑动窗口限流、Pydantic v2 全量参数校验、**20 项自动化验收用例** |
| 部署 | Dockerfile + docker-compose（web + postgres:16），健康检查探针 |
| 运行 | `http://127.0.0.1:8010`，演示账号 `13800000000 / 123456` |

### 一句话自我定位

> 这不是一个"调用一次大模型 API 就算 AI 功能"的演示项目。它的技术含量集中在四件事：**把外部依赖都设计成可降级**、**把横切关注点（鉴权/日志/限流/校验/异常）做成基础设施而不是散落在业务里**、**用自己实现的 RAG 与 SSE 补上 AI 工程链路**、**每一个优化都有可复现的验证数据**。

## 三、专题一：手写 JWT 鉴权

### 为什么不用 PyJWT

沙箱环境禁止 `pip install`，PyJWT 装不上。这看起来是限制，实际成了加分项：**JWT 的本质就是三段 Base64Url 拼接 + HMAC 签名**，用标准库 40 行就能写出等价实现，而且面试时可以完整讲清签名与验签过程。

### 实现要点

```
token = base64url(header) + "." + base64url(payload) + "." + base64url(signature)
payload = {"uid": <用户ID>, "exp": <过期时间戳>}
signature = HMAC-SHA256(secret, header + "." + payload)
```

| 设计点 | 做法 | 面试口径 |
|---|---|---|
| 密钥管理 | 取环境变量 `JWT_SECRET`，缺省值仅供本地开发 | "默认密钥可被伪造签名，生产必须注入，这是我在 README 里显式标注的部署前置条件" |
| 过期控制 | payload 带 `exp`，有效期 7 天，验签后再校验时间 | "签名只证明没被篡改，不证明没过期，两者必须都校验" |
| 失败语义 | 一律抛 401，不区分"签名错"还是"过期" | "对外不泄露失败细节，避免给攻击者提供探测信号" |
| 前端配合 | 请求拦截器注入 `Authorization: Bearer <token>`；响应拦截器遇 401 即清 token 并跳登录 | "token 失效的处理是全局的，不是每个页面各写一遍" |

### 验证方式

自动化用例覆盖三种攻击面：**无 token → 401**、**垃圾字符串 token → 401**、**用错误密钥伪造签名 → 401**，同时验证**合法 token 全业务 200** 且**跨用户读他人会话/订单被拒**。

## 四、专题二：双栈数据库抽象

### 为什么做双栈

演示环境用 SQLite（零配置、单文件、可直接随项目分发）；生产环境需要 PostgreSQL（并发、事务、类型系统）。如果业务代码写死 SQLite 方言，迁移就是一次重写。所以把差异全部收敛到一层。

### 三个必须解决的方言差异

| 差异 | SQLite | PostgreSQL | 抽象层做法 |
|---|---|---|---|
| 占位符 | `?` | `%s` | 业务层**统一写 `?`**，`db.py` 内部按方言改写 |
| 自增主键 | `INTEGER PRIMARY KEY AUTOINCREMENT` | `SERIAL` | DDL 生成时按方言替换 |
| 插入取主键 | `cursor.lastrowid` | `INSERT ... RETURNING id` | 统一走 `RETURNING id`，SQLite 3.35+ 已支持 |
| 表结构自省 | `PRAGMA table_info` | `information_schema.columns` | `columns()` 内部分派 |

### 一个真实踩坑

购物车表是**复合主键**（`user_id + med_id`），没有 `id` 列。统一用 `RETURNING id` 后这张表必然报错。解决方式是维护 `NO_ID_TABLES` 白名单，插入时跳过主键回填。这个细节面试时值得主动提——它说明抽象层不是"想当然统一"，而是**识别出例外并显式处理**。

## 五、专题三：限流与可观测性

### 限流：内存滑动窗口

```
默认 300 次 / 分钟 / IP
收紧规则：/api/sms/code → 5/min   /api/login → 10/min   /api/register → 5/min
超限统一返回 429，中文提示由前端直接 Toast
```

**为什么是滑动窗口而不是固定窗口**：固定窗口在窗口边界会出现双倍突发（59 秒打满 + 61 秒再打满）。滑动窗口按"最近 60 秒内请求数"统计，边界无漏洞。

**诚实项**：当前是**进程内存**实现，多 worker 或重启不共享，生产需换 Redis。这一点我会主动讲，因为面试官往往正是在等你暴露这个认知。

### 可观测性三件套

| 能力 | 实现 | 价值 |
|---|---|---|
| 结构化日志 | RotatingFileHandler（10MB × 3 轮转），单行含 `method / path / status / ms / ip / uid` | 一次请求一行，可以直接 grep 出慢接口和异常用户 |
| 统一异常 | 422 校验错误、401/429 业务错误、500 未捕获，响应结构恒为 `{ok, msg, detail}` | 前端只需一套错误处理逻辑 |
| 耗时审计 | 中间件注入 `X-Process-Time` | 性能问题不靠猜 |

### 参数校验：把 dict 赶出路由

改造前大量路由签名是 `body: dict`，任何字段都可能缺失。改造后 **20 个 Pydantic v2 模型覆盖全部写接口**，`extra=ignore`、字符串自动去空白，并由 `human_error()` 把框架的英文校验错误渲染成中文（如"缺少参数：手机号""手机号格式不正确"）。

结果：`body: dict` 路由数量归零，422 报错从"看不懂"变成"能直接给用户看"。

## 六、专题四：RAG 知识库检索增强 ⭐

这是整个项目技术含量最高、面试最能展开的部分。

### 6.1 为什么需要 RAG

大模型直接回答医疗问题有两个不可接受的问题：

1. **幻觉**——它会编造剂量、禁忌，医疗场景零容忍；
2. **不可追溯**——用户和医生都不知道答案依据是什么。

RAG（Retrieval-Augmented Generation）的思路是：**先从可信知识库里检索出相关原文，再让模型基于原文作答**。答案有出处、可核查，而且模型不需要"记住"医学知识。

### 6.2 链路全景

```
问诊提问
   │
   ├─① 检索：查询文本 → Embedding → 与向量库里 48 个块算余弦相似度 → 取 Top-3
   │        （相似度 < 0.32 视为未命中，不注入，避免"检索到无关内容反而干扰"）
   │
   ├─② 拼装 Prompt：
   │        [角色设定] + [检索到的资料片段（带出处）] + [最近 6 轮对话] + [本次提问]
   │
   ├─③ 生成：命中则让模型基于资料作答；模型不可用则用知识库摘要兜底
   │
   └─④ 回流：SSE 逐字推送，done 帧回传命中的知识库文件，前端展示"参考资料"标签
```

### 6.3 知识库资产

| 项 | 数字 |
|---|---|
| 知识库文件 | 8 篇（发热与呼吸道 / 消化系统 / 心血管与内分泌 / 皮肤与过敏 / 儿科 / 妇产科 / 神经与疼痛 / 用药安全与急症） |
| 语义块 | **48 块** |
| 切块参数 | 目标 320 字，相邻块重叠 60 字 |
| 向量维度 | 1024（远端 `text-embedding-v3`） |
| 召回参数 | Top-K = 3，相似度阈值 0.32 |

**切块为什么用重叠**：医学文本里"用法用量"常常跨段落，硬切会把"一次 0.5g"和"一日三次"分到两块。60 字重叠保证关键信息不会被切断，这是文本切分的经典权衡（chunk 越大上下文越完整但检索越不精准，越小越精准但语义越碎）。

### 6.4 关键设计一：向量库自己实现

Chromadb / FAISS 装不上，于是用 SQLite 表 `kb_chunks` 做向量存储：

```
kb_chunks(id, src, ord, text, dim, mode, vec BLOB, hash)
vec    = struct.pack("<1024f", *向量)      # 二进制紧凑存储
检索   = 逐行读 BLOB → struct.unpack → 与查询向量点积
隔离   = WHERE dim=? AND mode=?            # 1024维远端空间 与 256维本地空间互不污染
```

**面试表述**："我没有把向量存成 JSON 文本，而是 `struct` 打包成 BLOB。原因是 48 块 × 1024 维如果用 JSON 存，体积和解析开销都是数量级浪费。检索阶段数据量小，直接在应用层做点积完全够用；数据量上到十万级才会引入专用向量库，这时的瓶颈是索引结构而不是存储格式。"

### 6.5 关键设计二：双通道 Embedding 降级

这是整个项目最有说服力的一处设计。

| 通道 | 实现 | 触发条件 |
|---|---|---|
| 主通道 | 远端 `text-embedding-v3`（OpenAI 兼容协议），1024 维 | 正常 |
| 降级通道 | 本地字符 bi-gram 哈希向量，256 维 | 远端超时 / 报错 / 无 Key |

降级不是"报错退出"，而是**自动切换 + 写入日志 + 继续服务**。因为远端的 `dim` 是 1024、本地是 256，两者向量空间不可比，所以索引表用 `dim + mode` 双字段隔离，两套索引各自独立、互不干扰。

**这带来的直接收益**：项目在**无网络、无 API Key、额度耗尽**三种情况下都能正常启动并提供问诊服务。而实测中这种情况是真实发生的——见 6.6。

### 6.6 真实状态：LLM 额度耗尽，RAG 仍在工作

实测数据（面试时可以直接讲这一段）：

| 接口 | 结果 |
|---|---|
| `/chat/completions`（对话） | **HTTP 403 insufficient_quota**（免费额度耗尽） |
| `/embeddings`（向量） | **200，1024 维** ✅ |

也就是说：**向量通道可用，生成通道不可用**。系统的应对是三级降级：

```
source=llm   模型正常，基于 RAG 资料作答          ← 有额度时的主路径
source=kb    模型不可用，用检索到的知识库摘要作答   ← 当前实际状态
source=rule  知识库也没命中，走关键词规则兜底       ← 最底兜底
```

**这一段是面试时的最高价值点**：它证明我不是"跑通一次就交付"，而是真的考虑并验证了依赖失效时系统怎么活。任何依赖外部服务的系统都必须回答"它挂了怎么办"，我的答案是三级降级 + 每一级都有真实分支。

### 6.7 检索质量实测

用三个典型问诊问题验证召回准确度：

| 查询 | Top-1 命中文件 | 相似度 |
|---|---|---|
| 发烧到 39 度怎么办 | `01-发热与呼吸道.md` | 0.714 |
| 吃完头孢能喝酒吗 | `08-用药安全与急症.md` | 0.688 |
| 孩子拉肚子脱水 | `05-儿科.md` | 0.812 |

三个问题分别覆盖「症状」「用药禁忌」「特殊人群」，都命中了正确科室文件，说明切块粒度与阈值设置合理。

### 6.8 与 LangChain 的对标关系

项目原定技术栈是 LangChain，但沙箱禁止安装。实现时**按其抽象职责逐个对标自研**，这样面试被问到 LangChain 也能答得上来：

| LangChain 抽象 | 本项目对应实现 | 职责 |
|---|---|---|
| `Document` | `rag.Document` dataclass | 文本 + 元数据容器 |
| `RecursiveCharacterTextSplitter` | `rag.split_text()` | 按 markdown 小节 + 句子递归切块，带重叠 |
| `Embeddings` | `rag.embed()` | 双通道向量化 |
| `VectorStore` | `kb_chunks` 表 + `search()` | 向量存取与相似度检索 |
| `Retriever` | `rag.search(k, min_score)` | Top-K + 阈值过滤 |
| `Chain` | `build_msgs()` + `doctor_reply()` | 检索结果注入 prompt 并调用模型 |

**面试口径**："我用标准库实现了 LangChain 对应组件的等价能力，所以我知道每个抽象解决什么问题、边界在哪。换成真实 LangChain 时，这套分层不需要动，只是把实现类替换掉。"

## 七、专题五：SSE 流式对话 ⭐

### 7.1 改造前的问题

原实现 `POST /api/chat/send` 是**一次性返回**：用户点发送 → 前端 await → 后端检索 + 调模型（2–3 秒）→ 一次返回完整回复。

用户体验是**2–3 秒白屏无反馈**，这在医疗问诊场景尤其糟糕——用户会以为卡死了，反复点击。

### 7.2 为什么选 SSE 而不是 WebSocket

| 方案 | 适合场景 | 为什么本项目不选 / 选 |
|---|---|---|
| 轮询 | 低频状态查询 | 每次都要完整 HTTP 往返，延迟与开销都不可接受 |
| WebSocket | **双向**实时通信（聊天室、协同编辑、游戏） | 问诊是"用户问→服务端答"的单向流，为此维护长连接 + 心跳 + 重连的心跳成本不划算 |
| **SSE** | **服务端→客户端单向流** | 原生 HTTP、自动断线重连、能用现有鉴权中间件、无额外协议握手 ✅ |

**核心判断**：**通信方向决定协议选型**。单向流用 SSE，双向才上 WebSocket。

### 7.3 一个必须自己解决的坑：EventSource 不够用

浏览器原生 `EventSource` 有两个硬限制：

1. **只支持 GET**，无法用 POST 提交消息体；
2. **不能自定义请求头**，无法携带 `Authorization: Bearer <token>`。

所以最终用 **`fetch` + `ReadableStream` 手工解析 SSE 帧**（`frontend/src/api/stream.js`）：

```js
const reader = res.body.getReader()
const decoder = new TextDecoder('utf-8')
let buf = ''
while (true) {
  const { value, done } = await reader.read()
  if (done) break
  buf += decoder.decode(value, { stream: true })   // ← stream:true 处理跨包的多字节字符
  let cut
  while ((cut = buf.indexOf('\n\n')) >= 0) {       // ← 按空行切帧
    const frame = buf.slice(0, cut)
    buf = buf.slice(cut + 2)
    if (!frame.startsWith('data:')) continue
    const obj = JSON.parse(frame.slice(5))
    if (obj.t === 'delta') onDelta(obj.v)
    else if (obj.t === 'done') onDone(obj)
  }
}
```

**两个容易讲出深度的细节**：

- `decode(value, {stream: true})`：网络分片可能把**一个中文字符切成两半**，必须用流式解码器保留跨包字节，否则会出现乱码。这是 SSE 中文场景的经典坑。
- `buf` 缓冲区：一次 `read()` 可能返回半个帧或两个半帧，必须按 `\n\n` 边界累积解析，不能假设"一次读到一帧"。

### 7.4 帧协议设计

```
data: {"t":"delta","v":"根据您描述的"}      ← 增量文本，前端追加
data: {"t":"delta","v":"症状，建议…"}
data: {"t":"done","reply":"<完整回复>","source":"llm|kb|rule","hits":[{"src":"01-发热与呼吸道.md","score":0.71}]}
```

| 设计点 | 理由 |
|---|---|
| `delta` 与 `done` 分离 | 前端可以只做增量渲染，`done` 帧承载元信息（来源、命中文件），不污染文本 |
| `done` 回传完整 `reply` | 前端可与增量拼接结果比对，也可直接覆盖，**避免累积误差** |
| `done` 回传 `hits` | 前端展示"📚 参考资料"标签，让 RAG 可解释性对用户可见 |
| 响应头 `X-Accel-Buffering: no` + `no-cache` | 防止 Nginx 等反向代理缓冲整个响应，导致"流式"退化成一次性返回 |

### 7.5 前端体验改造

```js
// 乐观渲染：先插入用户消息 + 空的医生气泡，再逐帧填充
msgs.value.push({ role: 'user', text: t })
const idx = msgs.value.push({ role: 'dr', text: '', typing: true }) - 1
```

- **首字可见时间从 2–3 秒降到 100 毫秒级**；
- 回复中显示闪烁光标 `▋`，发送按钮禁用并显示"回复中"，防止重复提交；
- 完成后展示命中的知识库文件，把"AI 为什么这么答"变成用户可见。

### 7.6 后端实现要点

```python
return StreamingResponse(gen(), media_type="text/event-stream", headers={
    "Cache-Control": "no-cache",
    "X-Accel-Buffering": "no",
})
```

- 生成器内部：**先校验会话归属与状态 → 落库用户消息 → 检索 → 流式生成 → 最后落库完整回复**。校验放在流开始前，失败直接返回普通 JSON（404/403），前端按普通错误处理。
- 模型流式读取用 `urllib` 逐行读 `data:` 帧、解析 `choices[0].delta.content`，异常时**静默结束不抛错**，由调用方降级——保证"模型挂了也只是慢一点，不会 500"。

## 八、专题六：数据库索引优化

### 8.1 问题定位

`bailing.db` 原先**没有任何自建索引**，而几乎所有列表/详情接口都在按 `user_id`、`chat_id`、`status` 过滤。这意味着每次查询都是**全表扫描**。

具体表现：「我的订单」页面要**全量拉取用户订单**再渲染，页面高度达到 6519px 才渲染完；订单量增长时延迟线性上升。

### 8.2 建索引的判断依据

建索引不是"哪个字段查得多就加"，而是**按真实查询模式建复合索引**：

| 索引 | 表(列) | 对应查询 |
|---|---|---|
| `idx_chats_user` | chats(user_id, status) | 我的问诊按状态筛选 |
| `idx_msgs_chat` | msgs(chat_id, id) | 会话消息按会话取并保序 |
| `idx_orders_user` | orders(user_id, status) | 我的订单分状态 |
| `idx_appts_user` | appts(user_id, status) | 我的挂号 |
| `idx_coupons_user` | coupons(user_id, status) | 我的卡包 |
| `idx_notices_user` | notices(user_id, read) | 未读数统计 |
| `idx_kb_dim` | kb_chunks(dim, mode) | RAG 向量检索按空间隔离 |
| …共 **18 条** | | |

**复合索引的字段顺序有讲究**：`(user_id, status)` 而非 `(status, user_id)`。因为查询一定是"先定位这个人，再筛状态"，`user_id` 是等值条件且区分度更高，放在最左列才能让索引真正生效（最左前缀原则）。如果反过来，`status` 只有几个枚举值，区分度极低，索引用不上。

### 8.3 双栈兼容

`CREATE INDEX IF NOT EXISTS idx_x ON t(a, b)` 这条语法在 **SQLite 和 PostgreSQL 上完全一致**，因此索引定义可以直接放进启动流程，无需方言分支。

启动时幂等执行（`ensure_indexes()`），已存在则跳过；某张表尚未创建时**捕获异常并记录跳过，不阻断启动**。

### 8.4 验证方式：不靠感觉，靠 `EXPLAIN`

索引是否真的生效，唯一可信的验证是执行计划：

```
SELECT * FROM orders WHERE user_id=1 AND status='待支付'
→ SEARCH orders USING INDEX idx_orders_user (user_id=? AND status=?)   ✅

SELECT * FROM msgs WHERE chat_id=1 ORDER BY id
→ SEARCH msgs USING INDEX idx_msgs_chat (chat_id=?)                    ✅

SELECT * FROM chats WHERE user_id=1 AND status='问诊中'
→ SEARCH chats USING INDEX idx_chats_user (user_id=? AND status=?)     ✅

SELECT * FROM kb_chunks WHERE dim=1024 AND mode='remote'
→ SEARCH kb_chunks USING INDEX idx_kb_dim (dim=? AND mode=?)           ✅
```

四条高频查询全部命中索引，无一条是 `SCAN`（全表扫描）。**这四条验证已经写成自动化用例**，改代码后回归即可确认没有退化。

## 九、面试问答预演

### Q1：介绍一下你这个项目里最有技术含量的部分

> 是问诊链路的 RAG + 流式输出。RAG 解决的是医疗场景下的幻觉问题——不能让模型凭空编造剂量和禁忌，所以先检索可信知识库再作答，答案可追溯到具体科室指南。流式解决的是体验问题——改造前用户要等 2–3 秒白屏，现在是首个字 100 毫秒内出现、逐字输出，同时把命中的知识库文件展示给用户。
> 更关键的是这两条链路都有**降级设计**：模型额度耗尽时用知识库摘要兜底，向量接口不可用时切本地哈希向量。实测我的对话接口就是 403 额度耗尽的状态，但问诊功能依然完整可用。

### Q2：为什么用 SSE 不用 WebSocket？

> 看通信方向。WebSocket 是双向长连接，适合聊天室、协同编辑这类客户端也要主动推的场景。问诊是"用户问一句、服务端答一段"的单向流，用 WebSocket 要额外维护连接保活、心跳、重连和鉴权握手，成本不对等。SSE 走原生 HTTP，能复用现有的 JWT 中间件和限流，断线还能自动重连。
> 补充一个实现细节：我没用浏览器原生 `EventSource`，因为它只支持 GET、不能带自定义请求头，而我需要 POST 提交消息体 + Bearer token，所以用 `fetch` + `ReadableStream` 手工解析 SSE 帧。

### Q3：SSE 实现里你踩过什么坑？

> 两个。一是中文截断——网络分片可能把一个 UTF-8 多字节字符切成两半，必须用 `TextDecoder.decode(value, {stream: true})` 保留跨包字节，否则出现乱码。二是一次 `read()` 不保证返回完整帧，可能半个或两个半帧，所以要用缓冲区按 `\n\n` 边界累积解析。另外后端要设 `X-Accel-Buffering: no`，否则经过 Nginx 会被整体缓冲，"流式"变成一次性返回。

### Q4：你的 RAG 检索怎么保证质量？

> 三个环节。切块：按 markdown 小节加句子递归切，目标 320 字、重叠 60 字，重叠是为了避免"一次 0.5g"和"一日三次"被切到两块。召回：Top-3 + 相似度阈值 0.32，低于阈值视为未命中、不注入，因为检索到无关内容反而会干扰模型。验证：用三个典型问题实测，发烧 39 度命中发热科文件 0.714，头孢配酒命中用药安全 0.688，儿童腹泻命中儿科 0.812，分别覆盖症状、用药禁忌、特殊人群三种类型。

### Q5：向量库为什么自己写，不用 Chroma？

> 环境装不上是一方面，另一方面是数据量根本不需要。48 个块、1024 维，直接把向量用 `struct.pack` 存成 BLOB，检索时 unpack 后做点积，性能完全够。真正的成本在存储格式而不是检索算法——如果用 JSON 存 48×1024 个浮点数，体积和解析开销都是两个数量级的浪费。数据量到十万级才会引入专用向量库，那时瓶颈变成索引结构（HNSW/IVF）而不是存储。

### Q6：怎么处理 LLM 不可用？

> 三级降级，每一级都真的跑过。第一级模型正常：基于 RAG 资料作答，`source=llm`。第二级模型不可用：用检索到的知识库摘要组织回复，`source=kb`——这是我当前的实际状态，因为免费额度用完了，对话接口返回 403。第三级知识库也没命中：走关键词规则兜底，`source=rule`。所有降级都会写结构化日志，并且 `done` 帧会把 source 告诉前端，用户和运维都能看出当前是哪种模式。

### Q7：JWT 为什么手写？安全性怎么保证？

> 标准库环境装不了 PyJWT，但 JWT 本质就是两次 Base64Url 编码加一次 HMAC-SHA256 签名，40 行能写完。安全性上做三件事：密钥从环境变量读，默认值只用于本地开发并在 README 标注为部署必改项；签名验证和过期验证都做，签名只证明没篡改、不代表没过期；失败统一返回 401 不区分原因，避免给攻击者探测信号。自动化用例覆盖了无 token、垃圾 token、伪造签名三种情况。

### Q8：限流怎么做的？有什么局限？

> 内存滑动窗口，默认 300 次/分钟/IP，短信验证码 5 次、登录 10 次、注册 5 次单独收紧。选滑动而不是固定窗口，是因为固定窗口在边界会双倍突发——59 秒打满、61 秒再打满。
> 局限我很清楚：进程内存实现，多 worker 或重启不共享，生产必须换 Redis。我把这条写进了文档的"已知局限"，因为它属于架构级取舍而不是疏漏。

### Q9：索引是怎么定的？怎么证明有效？

> 按真实查询模式定，不是按字段热度。所有列表查询都是"先按 user_id 定位、再按 status 筛选"，所以建复合索引 `(user_id, status)` 而不是 `(status, user_id)`——最左前缀原则下，区分度高的等值条件必须在最左列，而 status 只有几个枚举值，单独放最左根本用不上。
> 有效性用 `EXPLAIN QUERY PLAN` 证明，四条高频查询全部 `USING INDEX`，没有一条 `SCAN`。这四条已经写成自动化用例，防止后续改动导致索引失效。

### Q10：双栈数据库迁移到 PG 有什么坑？

> 占位符 `?`→`%s`、自增 `AUTOINCREMENT`→`SERIAL`、插入取主键 SQLite 用 `lastrowid` 而 PG 要 `RETURNING id`。我统一走 `RETURNING id`，因为 SQLite 3.35+ 也支持。
> 最大的坑是购物车表——它是复合主键没有 id 列，统一 `RETURNING id` 直接报错。所以维护了 `NO_ID_TABLES` 白名单显式跳过。这件事让我意识到，抽象层不是把差异"想当然抹平"，而是要识别例外并显式处理。

### Q11：为什么后端是单文件？不怕难维护吗？

> 67 条路由放在 `app.py` 里，但横切关注点全部拆到 `core.py`（日志/限流/异常/CORS）、`db.py`（数据访问）、`schemas.py`（校验）、`rag.py`（AI 增强）。所以"单文件"只是路由挂载在一起，不是逻辑耦合在一起。
> 取舍理由：这是个演示项目，单文件让面试官能一次读完所有业务逻辑，降低理解成本。如果按域拆成 `routers/user.py`、`routers/chat.py` 也可以，但会分散阅读注意力。规模再大必须拆，这是我的判断而不是习惯。

### Q12：这个项目的已知局限是什么？

> 我会主动说明四条。一，大模型当前额度耗尽，处于知识库兜底模式，`source=kb` 而不是 `llm`。二，PostgreSQL 只做了代码层与 DDL 转换验证，没有真库联调，需要一台有 Docker 的机器跑 `docker compose up` 终验。三，支付是模拟的，`/order/pay` 直接改状态，没有接微信/支付宝回调。四，限流和验证码是进程内存，生产必须换 Redis。
> 以及一条非技术限制：医疗问诊涉及资质合规和等保，真实商用不在这个项目范围内。

### Q13：如果给你更多时间，下一步做什么？

> 按性价比排三档。第一档已经做完：RAG、SSE、索引、本文档。第二档是列表分页、验证码持久化、响应模型 `response_model` 补全让 OpenAPI 文档完整、几处前端布局缺陷。第三档是多模态（皮肤图片识别）、医生端和管理端、Docker 多阶段构建、CI 流水线。
